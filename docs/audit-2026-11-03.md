# Project audit — 3 November 2026

The audit covered every inner card, shared data and rendering code, the editor, Home Assistant lifecycle, build output, and existing test infrastructure. Three parallel reviewers covered reading cards, forecasts and sheets, and graphics and maps; the main review covered shared sources, records, configuration, localization, and integration. Cross-review caught additional source/unit and remote-location inconsistencies before verification.

The existing design is retained. No stylesheet, visual asset, hand-tuned sky preset, screenshot baseline, or dependency version was changed.

## Confirmed issues fixed

| Area | Corrections |
| --- | --- |
| Home Assistant/configuration | Repeated invalid configurations keep reporting errors. Changes to the legacy language field now refresh the card, editor, and dashboard title. Unrelated entity updates still skip rendering. |
| Sensor sources | Blank numeric states no longer become zero; unavailable weather overrides no longer supply stale attributes; weather entities can supply compass-point wind bearings. |
| History | Pressure history follows the effective reading source, converts from recorded units, and clears the previous source immediately. Rain totals refresh when display units change and reject delayed responses after the source is removed. Temperature history supports another weather entity as its source. |
| Translation loading | Concurrent cards share the pending language fetch; outdated language replies are ignored; returning to English or falling back after a failed load redraws the previous translation. |
| Air quality | Blank readings stay absent; sibling pollutant discovery follows current states; sheets reuse cached registry siblings. Gas concentrations in ppm convert consistently with ppb. |
| Pressure | Pa uses the correct thresholds and gauge range. A zero value without a recognized unit produces valid geometry. |
| Precipitation | Tile and sheet include the same current-hour interval. Tomorrow is calculated by calendar date across daylight-saving transitions. |
| UV | Today's protection window no longer ends at a low reading from tomorrow. |
| Averages | Invalid recorder rows are skipped without discarding otherwise valid climate statistics. |
| Remote locations | Sky, sun, moon, hourly sun markers, and map pin icons follow the weather entity's location. Home sun data remains authoritative for home. Solar schedules are bounded and cached. |
| Alerts | Unchanged alert records refresh their wording when the language, clock format, timezone, or expiry changes. |
| Next hour | Duplicate timestamps do not fabricate sub-hourly resolution; the final old sample expires instead of extending indefinitely. |
| Sheets | Keyboard focus survives control redraws, including a day arrow becoming disabled. External condition names and unfamiliar units are escaped at text boundaries. |
| Maps | Inactive wind drawings stop requesting animation frames. Closed sheets release pending MapLibre instances and ignore late initialization. Hidden/closed maps skip new grid requests. Animation preferences invalidate drawings. Missing temperature limits stay absent, URL attributes are escaped, and polar coordinates are bounded to the map projection. |

## Performance measurements

Measurements use the production bundle in headless Chromium 156 at 1280 × 900, with the repository's rainy full-card fixture and `local_only: true`. The renderer reported ANGLE/Vulkan using SwiftShader software rendering. Each value below is the median of three isolated runs. Routed local assets do not represent a cold internet connection, and a sampled click duration is not field INP.

| Measurement | Animation enabled | Animation disabled |
| --- | --- | --- |
| Largest contentful paint | 252 ms | 260 ms |
| Cumulative layout shift | 0 | 0 |
| Wind-sheet click duration | 64 ms | 72 ms |
| 1,000 unrelated entity updates | 1 ms; zero renders | 1 ms; zero renders |
| Main-thread task time during first 2 s after mount | 1,588 ms | 466 ms |
| Main-thread task time during 2 s after a 10 s warm-up | 1,563 ms | 2.27 ms |
| Main-thread task time during 2 s offscreen | 17 ms | 21 ms |

The local LCP and CLS samples fall within the good ranges in the linked Web Vitals guidance. Field INP was not collected. With animation disabled, ongoing work settles close to idle after initialization. With animation enabled, rain remains expensive under this software renderer; the offscreen measurements verify that the hidden card avoids most ongoing work.

No third-party requests occurred in these local-only samples. The normal initial view requested the main bundle, seven cloud images, and the moon relief texture; it did not request MapLibre. The entry bundle is 794,920 bytes uncompressed, or 252,832 bytes using Node's default gzip settings. Requested art totals 791,026 bytes. These are artifact sizes, not measured wire transfer sizes.

The initial 2.057 s CPU profile attributes about 1,170 ms to native `drawImage` calls, primarily the rain/glass and sky canvas paths. It also includes roughly 262 ms of initial cloud texture/noise construction. This establishes a rendering bottleneck in the measured environment, not evidence that the same cost occurs on a hardware-accelerated tablet. Removing intermediate canvases would require pixel comparisons and hardware profiling; no such architectural change was made during this audit.

Performance follow-up, in priority order:

1. **High measured cost, hardware impact unmeasured:** profile warmed rain/glass rendering on a target wall tablet before changing canvas composition. Compare native `drawImage`/GPU-copy time, frame delivery, and existing snapshots for any experiment. Existing `weather_animation` and `low_power` settings remain available; defaults are unchanged.
2. **Potential cold-network cost:** measure the served bundle/art with real Home Assistant cache and compression headers before deciding whether to split more code or change assets. The fixture cannot establish a transfer-time saving.
3. **No observed local regression:** leave unrelated entity-update filtering and initial layout behavior intact. The measured burst caused zero renders and no layout shift was recorded.

## Rain texture follow-up

A subsequent rendering profile put 38% of sampled self time in `texImage2D`. The shared glass renderer kept only the last card's sky, so alternating cards bypassed its three-frame upload throttle. Each source sky now has its own texture pair, with a four-source limit. Beyond that limit the least recently drawn pair is reused, avoiding repeated GPU allocation; additional cards can still require uploads on every draw.

Cached animated skies refresh no more often than every third draw and 125 ms. Drops still animate at the existing frame rate. First draws, still repaints, changed dimensions and clock rewinds refresh immediately. The shader, texture resolution, filtering and compositing are unchanged. Textures are released for hidden, dry, disabled and disconnected cards. The visibility callback also uses the latest entry when a rapid move queues multiple changes in one delivery.

The comparison used the production bundle, the rainy local-only fixture, Chromium 156.0.8078.4 with SwiftShader, a 1280 × 900 viewport, a 10-second warm-up and a 3-second sample. Two-card runs placed two 600-pixel-wide cards side by side. Values are medians of three runs, normalized by actual sample duration; the main-thread measure is CDP `TaskDuration`.

| Measurement | Before | After |
| --- | --- | --- |
| One card: texture uploads per second | 13.96 | 14.64 |
| One card: main-thread task ms per second | 790 | 785 |
| Two cards: texture uploads per second | 64.69 | 21.61 |
| Two cards: measured texture-upload ms per second | 47.85 | 14.41 |
| Two cards: main-thread task ms per second | 939 | 769 |
| Two cards: glass draws per second, combined | 32.34 | 32.09 |

The two-card sample reduced uploads by 67% and main-thread work by 18%, with a similar draw rate. The single-card sample showed no clear improvement: this software renderer ran slowly enough that the existing three-draw gate already limited uploads below eight refreshes per second. Faster devices can benefit from the added time gate, but that hardware impact has not been measured.

A direct comparison against the committed renderer produced identical rain pixels in 36 combinations of three rain tiers, two canvas sizes, two device scales and three animation times, using a fixed multicolour sky. This verifies rendering with the same source pixels; a moving sky's reflection now refreshes less often. Regression tests cover texture isolation, invalidation, bounded reuse, context loss, visibility and card removal.

Firefox follow-up runs exposed clickable forecast rows entering native text dragging after earlier presses selected text across the list. Interactive rows now prevent text selection, consistent with the card's other controls. The original pointer path and highlight assertions remain, with an added check that dragging a row leaves no text selected.

## Remaining limits

This is a source and automated runtime audit, not a claim that every integration, device, or future browser is defect-free. Live third-party weather/map services were replaced by fixtures in browser performance measurements. Low-end wall-tablet hardware and field interaction data were not measured.

The dependency audit reports one moderate development-tool advisory in transitive `minimatch@10.2.6`, reached through ESLint and its compatibility plugin. It is not imported into the shipped card. The advisory concerns attacker-controlled glob patterns with optimization level 2 or greater; the patched release is 11.0.1. A forced major-version override was not introduced in this UI/runtime fix set. See [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249).

The review followed the current [Home Assistant custom-card contract](https://developers.home-assistant.io/docs/frontend/custom-ui/custom-card/) and [weather entity documentation](https://developers.home-assistant.io/docs/core/entity/weather/). Lab measurements should be read separately from field Core Web Vitals, as described in [Web Vitals](https://web.dev/articles/vitals).
